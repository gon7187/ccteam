# Командир v2: план Fable → гейт Sol → исполнители в worktree → git-агент → двойной финальный гейт

> Дата: 2026-09-02 · Статус: owner одобрил (гриль из 50 вопросов, все ветки закрыты) · Форма: **чистый prompt, движок не трогаем** (красные линии §三: «引擎零 LLM», «daemon 无自主内容决策循环», «永不主动 kill»). Все новые документы репо с этой даты пишутся на русском (решение owner, см. правку AGENTS.md §五.2 в разделе 15).

## 1. Область

Перекроить шаблон «🎯 Командир» (Telegram `/keys` + веб-карта Home/Charter) так, чтобы у каждой верхнеуровневой задачи появились: разведка → план в файле → гейт плана → исполнение в изолированных worktree с советником → интеграция git-агентом → двойной финальный гейт → merge. Плюс мониторинг нагрузки и живости сессий силами командира.

**Не в области**: любые правки движка (gateway, adapter, MCP schema, `status`, `session_list`); новые MCP-тулы; расписание для командира; workflow.yaml; новые skill; tag и release; переписывание существующих китайских доков.

## 3. Поток

1. Командир вызывает `status`, использует только объявленные vendor, модели и effort.
2. Спавнит разведчика GLM read-only, ждёт отчёт (`wait_seconds` или `session_dispatch` + `session_collect`). Гасит GLM.
3. Спавнит Fable с отчётом разведки. Fable пишет план в файл (раздел 4).
4. Спавнит Sol на ревью плана. Отклонил: Fable правит, Sol смотрит заново. Потолок 2 круга; третье расхождение = стоп и форматный доклад пользователю (раздел 5). Одобрено: Fable гасится, Sol остаётся советником.
5. Командир режет план на задачи, спавнит исполнителей по меткам, соблюдая зависимости и лимит 3 Luna. В каждую задачу кладёт: путь файла плана, id задачи, sid советника, правила раздела 6. Пауз на человека нет: план лежит в файле, пользователь может остановить в любой момент.
6. Исполнители работают в своих worktree (раздел 7), коммитят на своих ветках, докладывают командиру.
7. Все ветки закоммичены: командир спавнит git-агента (раздел 8). Интеграция, полные проверки.
8. Финальный гейт (раздел 9) смотрит интегрированный diff. Отклонил: замечания исполнителю, правка, оба ревью заново. Потолок 2 круга.
9. Одобрено: git-агент вливает в базовую ветку, push, PR draft→ready, merge в main при условиях раздела 8.
10. Уборка worktree и веток, советник гасится, командир собирает итог для пользователя.

## 4. Файл плана

- Путь: `<project>/.ccteam/plans/<YYYY-MM-DD>-<тема>.md`. `.ccteam/` уже в `.gitignore` любого ccteam-проекта после init; ничего дополнительно не трогаем. Пишет агент, не движок.
- Каждая задача: **id, исполнитель, зависимости, файлы (домен конфликта), критерий готовности**.
- Секция **Amendments**: каждая поправка после одобрения плана = запись с датой, автором (командир / Fable), причиной. Тело плана выше Amendments не переписывается.
- Единый источник истины: спор с планом решается поправкой в файле, не устными договорённостями в чате.

## 5. Гейт плана и форматный доклад при тупике

- Sol ревьюит план с правом блокировать. Потолок **2 круга** (план → замечания → правка → повторное ревью, дважды).
- Тупик: командир останавливает работу и присылает пользователю **три абзаца**: позиция Fable, позиция Sol, что нужно решить. Не транскрипты.
- То же правило потолка и формата действует на финальном гейте кода.

## 6. Советник

- Один общий Sol-советник (та же сессия, что ревьюила план). Исполнители обращаются напрямую через `session_dispatch` с `wait_seconds` (dispatch к соседу в том же проекте разрешён движком; ограничение «только потомки» стоит лишь на `session_stop`).
- Исполнитель **обязан** спросить советника перед любым отклонением от плана; по желанию, когда застрял.
- Совет **не обязателен** к исполнению, решает исполнитель. Исключение: советник считает план кривым в этом месте → исполнитель не правит план сам, а эскалирует командиру.
- Перепланирование: по умолчанию командир сам дописывает поправку в Amendments, советник её визирует, Fable не трогаем. Если советник говорит, что поправка ломает структуру плана, а не один шаг: свежий Fable перепланирует затронутый кусок, Sol ревьюит тем же циклом с потолком 2.
- Второй советник: командир поднимает его, если по `session_list` видно, что очередь к первому тормозит. Второй получает файл плана и **явный список задач**, которые обслуживает; не «всех, кто первый спросил».
- Советник живёт до одобрения кода финальным гейтом (правки по замечаниям гейта тоже исполнение плана), потом командир его гасит.
- Правила советника одинаковы для **всех** исполнителей (Luna, Terra, Sonnet, Haiku) без исключений.

## 7. Исполнители и изоляция

- Каждая задача плана в своём git worktree `../<repo>-wt/<id>` на ветке `task/<id>` от базовой ветки проекта (здесь `origin/dev`; в чужом проекте ветка разработки по его правилам, иначе default branch). Никогда в `/tmp`.
- Исполнитель гоняет затронутые тесты у себя, с `--test-threads=4`, коммитит на своей ветке сам (сообщения на английском по конвенции проекта).
- Не закрыл критерий готовности: докладывает командиру. Командир решает: повторить, спросить советника или поправка плана по разделу 6.
- Проект без git: worktree невозможны, исполнители работают по одному последовательно прямо в каталоге, git-агент не поднимается, командир пишет об этом в итоге. `git init` чужого каталога не делаем.

## 8. Git-агент

- Поднимается командиром один раз, когда все ветки задач закоммичены.
- Сливает ветки задач в `integration/<тема>` от базовой ветки. Базовая ветка остаётся чистой, пока гейт крутит круги.
- Гоняет **полный** набор проверок проекта по его CLAUDE.md/AGENTS.md (здесь: `cargo fmt --all -- --check`, clippy без новых warning, `cargo test --workspace`, веб-проверки). Красное = ошибка интеграции, идёт командиру, не исполнителю.
- Конфликты разруливает сам и перегоняет проверки. Если разрешение тронуло уже отревьюенные строки: командир возвращает diff финальному гейту.
- После одобрения гейтом: merge в базовую ветку, push, PR в main draft→ready (описание на английском), merge в main **merge commit, не squash**.
- **Условие merge в main**: одобрение обоих финальных ревьюеров **и** зелёный полный набор локальных проверок. CI добавляется третьим условием только если он в проекте есть и реально запускается; если его нет, не ждём.
- Уборка: worktree удаляются после интеграции, ветки задач после merge PR.
- Tag и release **вне** шаблона: только по отдельной явной команде owner.

## 9. Финальный гейт

- Свежий Opus + свежий Sol, обе сессии получают файл плана и diff `integration/<тема>` против базы, ничего больше.
- Одобрение = обе одобрили одну и ту же ревизию. Расхождение: замечания исполнителю, правка, **оба** ревью заново теми же гейт-сессиями (они ревьюеры, не авторы). Потолок 2 круга, дальше форматный доклад (раздел 5).
- Советник в приёмке не участвует: он соавтор.

## 10. Мониторинг нагрузки и живости

- Командир не тикает. Смотрит в **точках решения**: перед каждым spawn и на каждом уведомлении о завершении.
- Хост: `nproc`, `uptime`, `free -m` через свой shell. Сессии: `session_list` (`status`, `last_activity_seconds`, `waiting_approval`).
- Пороги по умолчанию (charter `routing.md` проекта может переопределить): load1 выше числа ядер; свободной памяти меньше 15 процентов; swap в работе.
- Лестница при перегрузе, по возрастанию: 1) не спавнить новых исполнителей, пока не отпустит; 2) через dispatch попросить работающих снизить `-j` и `--test-threads`, отложить тяжёлые тесты; 3) остановить самого свежего исполнителя через `session_stop`, задачу вернуть в план (ветка в worktree остаётся); 4) git-агента посреди интеграции и гейт не трогать никогда.
- Живость по статусам движка: `stale` = глянуть; `stuck` или тишина от 15 минут = dispatch «доложи статус» с `wait_seconds`; от 30 минут молчания = `session_stop` и respawn с той же задачей из плана. Сдохла (процесс вышел с ошибкой) = один dispatch на resume по sid; снова упала = свежий spawn. `waiting_approval: true` зависшей не считается.

## 11. Fallback, respawn, лимит детей

- Fallback только по типизированному доказательству: явный `status` или capability-ошибка spawn с `error_code` из `vendor_unavailable` / `model_unavailable` / `effort_unavailable`. Fable → Opus. Любая роль Sol (ревью плана, советник, финальный гейт) → свежий Opus. Остальное → одна попытка через Codex с лучшей объявленной моделью и максимальным effort. Любая другая ошибка (ACL, квота, бюджет, depth/cycle, timeout, network, internal) = вернуть как есть, без слепых повторов.
- Разведка: если пригодную GLM-сессию поднять не удалось, ровно одна попытка через Luna; не вышло = стоп по коду и честный доклад. При неизвестном исходе сначала сверка через `session_list` + `session_collect`.
- Живая сессия сдохла посреди работы: обычный respawn с файлом плана, это не fallback.
- `delegation.max_children` (дефолт 10) считает **активных** прямых детей, а отработавшая сессия висит в live map как `idle`. Поэтому командир гасит делегатов, которые больше не нужны (GLM после отчёта, Fable после одобрения плана, исполнителей после интеграции их веток). Текст шаблона обязан работать с дефолтной десяткой.

## 12. Честные границы

Всё поведение **prompt-soft**: движок не проверяет, была ли разведка, сколько кругов прошёл гейт, спросил ли исполнитель советника. Нарушение = деградация качества оркестрации, не ошибка движка. Это совпадает с «编排智能 100% 用户空间»; исполнение в gateway не добавлять.
