# Командир v3: три размера задачи, полосы по вендорам, динамический effort, балансировка третей

> Дата: 2026-09-04 · Статус: owner ответил на шесть открытых пунктов в чате (раздел 13), спек согласован · Форма: **prompt-слой + одна observability-карта на движок** (раздел 5.1): `status` отдаёт per-vendor токены за 24h и квоты подписок. Красные линии §三 не задеты («引擎零 LLM», «daemon 无自主内容决策循环», «永不主动 kill»): движок только считает и показывает, решает командир. Наследует v2 (`2026-09-02-commander-plan-gate-design.md`): всё, что здесь не переопределено, действует как в v2 (файл плана, Amendments, worktree, git-агент, мониторинг, потолок 2 круга, форматный доклад).

## 1. Зачем

v2 гоняет каждую задачу через полный цикл на `max`, и Claude тянет и планирование, и командование, и финальный гейт. Три беды: дорого на мелочи, лимиты одного вендора выжигаются раньше остальных, effort не зависит от сложности. v3 вводит три размера задачи, раскладывает роли по трём вендорам примерно равными третями, даёт командиру право выбирать effort и переключать вендора по четырём триггерам.

**Не в области**: правки gateway/adapter/`session_*`; новые MCP-тулы; расписание для командира; tag и release; перевод существующих доков. Единственная правка движка = раздел 5.1.

## 2. Ростер: основной вендор, фолбек, effort

| Роль | Основной | Фолбек | Effort по умолчанию |
|---|---|---|---|
| Командир | Claude Fable | Codex Sol | high |
| Разведчик | GLM flash (opencode) | Codex Luna | GLM без effort / Luna medium |
| Планировщик | Claude Fable | Codex Sol | max / xhigh |
| Ревьюер плана и советник | Codex Sol | свежий Claude Fable | high |
| Полоса A: бэкенд, деньги, ETL, сложная логика | Codex Luna | Claude Sonnet | high |
| Полоса B: фронт, маршруты, компоненты, интеграционный клей | Claude Sonnet | Codex Terra | high |
| Полоса C: тесты, доки, миграции по шаблону, boilerplate, инвентарь | GLM flash | Codex Luna | без / medium |
| Пре-гейт: линт, тесты, секрет-скан, чек-лист плана | GLM flash | Claude Sonnet | без / medium |
| Гейт 1 | Claude Fable | свежий Codex Sol | max |
| Гейт 2 | Codex Sol | свежий Claude Fable | high |
| Git-агент | GLM flash | Codex Luna | без / medium |

Правила ростера:

- Effort всегда ступень, которую `status` объявил для вендора. Ступени Claude: `low < medium < high < xhigh < max`; Codex: `low < medium < high < xhigh`; GLM: то, что объявит `status` (обычно без effort). «max» для Codex означает верхнюю объявленную ступень.
- Гейты всегда два разных вендора. Если фолбек сделал пару одновендорной, командир пишет это в итог.
- Каждый вендор держит одну полосу кода, одну роль суждения и одну роль механики: Claude = планировщик + гейт 1 + полоса B + командир; Codex = советник + гейт 2 + полоса A; GLM = разведка + полоса C + пре-гейт + git. Так по замеру сессии 2026-09-04 выходит примерно треть на каждого.

## 3. Три размера задачи

Командир классифицирует каждую верхнеуровневую задачу до первого spawn и пишет размер в файл плана (или, для мелочи, в бриф).

| Размер | Критерий | Цикл | Кто участвует |
|---|---|---|---|
| Мелочь | до 3 файлов, без жёстких признаков (раздел 5) | одна полоса → пре-гейт → один гейт | исполнитель полосы, GLM пре-гейт, гейт Sol high. Claude не участвует: задача полосы B уходит Terra |
| Средняя | план на страницу | разведка по желанию → план → один круг ревью плана → исполнители → пре-гейт → один гейт | Fable high пишет план, Sol high ревьюит и советует, исполнители по полосам, единственный гейт = свежий Sol high (всегда Sol, независимо от автора кода) |
| Крупная | всё остальное, любой жёсткий признак | полный цикл v2 | весь ростер, оба гейта |

Апгрейд размера один-направленный: мелочь, потянувшая четвёртый файл или жёсткий признак, становится средней; средняя, где план не влез в страницу или Sol заблокировал структуру, становится крупной. Даунгрейда нет.

## 4. Динамический effort

Командир задаёт `effort` в каждом `session_spawn` явно. Стартовая ступень берётся из раздела 2, затем корректируется:

- **Второй круг** (возврат с гейта или пре-гейта, замечания по существу): исполнитель поднимается на одну ступень, не выше объявленной верхней.
- **Boilerplate внутри крупной задачи** (полоса C): остаётся на нижней ступени, даже если задача крупная.
- **Жёсткая задача** (раздел 5) на любой полосе: не ниже `high`.
- **Гейт на дифф** повторного круга: та же ступень, что на первом круге; гейт не поднимается.
- Ниже `medium` у Claude и Codex командир не опускается: экономия не должна ронять качество ниже пре-гейта.

Выбранную ступень командир пишет в шапку брифа (раздел 8), чтобы фолбек стартовал с той же.

## 5. Жёсткие и гибкие задачи, балансировка третей

**Жёсткие** задачи идут по компетенции полосы, без балансировки: деньги, секреты и credentials, scope и границы ACL, миграции данных, всё, что трогает красные линии AGENTS.md §三.

**Гибкие** (большинство средних задач) командир отдаёт вендору с наименьшей долей расхода в текущем окне.

Снятие расхода перед каждым spawn: один вызов `status`, поле `tokens_24h` по вендору (раздел 5.1). Доля = токены вендора / сумма по трём. Сравнивать токены между вендорами в деньгах нельзя, но цель третей — лимиты подписок, а они у каждого вендора в его собственных токенах, поэтому доля по токенам и есть нужная метрика. Где `status` отдаёт окно подписки (`quota.windows[].used_percent`), оно старше токенов: вендор с `used_percent` выше 80 в любом окне считается лидером независимо от доли токенов.

**Порог перекоса 15 % относительных**: если доля лидера превышает треть больше чем на 15 % от трети (то есть выше 38,3 %), гибкие задачи уходят только двум отстающим, пока перекос не сойдёт ниже порога. Внутри двух отстающих выбирается меньший.

### 5.1. Карта на движок: `status` отдаёт расход и квоты по вендору

Observability, ноль LLM, ноль решений в движке. Три правки:

1. `crates/ccteam-im/src/progress_projection.rs`: рядом с `cost_24h_by_vendor` (USD) появляется `tokens_24h_by_vendor: BTreeMap<String, u64>` из тех же 24h-бакетов; `tokens_24h` суммарный остаётся.
2. `crates/ccteam-im/src/mcp/vendor_panel.rs`: `PanelRow` получает `spend_24h_usd: Option<f64>` (None для unpriced) и `tokens_24h: u64`; `render_panel` печатает их в строке вендора рядом с `budget=`. Литеральный тест на строку.
3. Проба квот подписок переезжает из `crates/ccteam-web/src/routes/vendor_quota.rs` (`VendorQuotaService`, кэш 5 мин) в `ccteam-core` (рядом с `vendor_quota.rs`), web и MCP `status` используют один сервис. `PanelRow` получает `quota: Option<VendorQuota>`; `render_panel` печатает `quota=<kind>:<used_percent>%[,reset=<rfc3339>]` по каждому окну, `quota=n/a` для `NotSubscription`/`Unavailable`. Пробуются только вендоры с метром (claude, codex, kimi); GLM/opencode = `n/a`, для него единственный сигнал = токены.

`status` для кросс-проектного admin-вызова агрегирует по всем видимым проектам; для привязанной сессии, как сейчас, по её проекту. Тесты: unit на агрегацию по вендору, литеральный лок строки панели, web-роут `GET /api/v1/vendors/quota` после переезда отдаёт тот же JSON (существующие тесты не меняются).

Честная граница: `status` показывает окно 24h ledger и окна подписки как их отдаёт вендор; ни одно из них не совпадает с «текущей задачей» командира. Командир балансирует по 24h, это осознанный выбор owner.

## 6. Фолбек: четыре триггера, один переход

Переключение на фолбек-вендора из раздела 2 по любому из четырёх триггеров:

1. **Capability-ошибка spawn**: `error_code` ∈ {`vendor_unavailable`, `model_unavailable`, `effort_unavailable`}. Правило v2 сохраняется дословно: любая другая ошибка spawn (ACL, квота, бюджет, depth/cycle, timeout, network, internal) = вернуть как есть.
2. **Два подряд** результата dispatch с `error_kind=server_overloaded` (529) либо `error` с текстом про session limit / rate limit.
3. **Тишина 30 минут**: `activity` = `stale` или `stuck` и `last_active` старше 30 минут, при `waiting_approval` ≠ true. Переключение сразу, без предварительного dispatch «доложи статус» (v2 §10 в этой части переопределён: тридцать минут тишины = сессия потеряна).
4. **Отчёт без «Статус: готово»** после ровно одного возврата исполнителю.

Переход дешёвый, потому что состояние лежит вне сессии: файл плана, ветка задачи в worktree с инкрементальными коммитами и строка «Ход» в секции задачи (раздел 8). Фолбек получает тот же бриф, тот же путь плана, ту же ветку и продолжает с места обрыва. **Один переход на задачу**; если и фолбек не закрыл задачу, командир останавливает задачу и докладывает по формату v2 §5.

Исходную сессию командир останавливает через `session_stop` до spawn фолбека (лимит `max_children`, v2 §11).

## 7. Пре-гейт GLM

До любого дорогого гейта задача проходит пре-гейт GLM: линт проекта (здесь `cargo fmt --all -- --check`, clippy на затронутом crate), затронутые тесты, секрет-скан (`gitleaks detect` если установлен, иначе grep по типовым паттернам ключей и токенов), соответствие чек-листу плана (каждый пункт критерия готовности отмечен в отчёте исполнителя). Выход: список pass/fail. Fail = один возврат исполнителю до гейта, без участия Fable и Sol. Пре-гейт читает дифф ветки задачи против базы, не весь репозиторий.

Повторный круг гейта смотрит только дифф с прошлой ревизии. Потолок два круга, дальше форматный доклад.

## 8. Бриф исполнителя: отдельный файл

Шаблон брифа живёт в `<project>/.ccteam/briefs/executor.md` (gitignored, пишет агент). Командир заполняет шапку и передаёт содержимое в `task` целиком: одна задача, одна свежая сессия, один ход. Обязательные разделы **жирным**, потому что возврат стоит как вся задача:

- **Шапка**: размер задачи, полоса, effort, id задачи, абсолютный путь файла плана, ветка `task/<id>`, worktree, sid советника (если есть).
- **Задача**: критерий готовности из плана дословно.
- **Границы**: файлы домена конфликта; что трогать нельзя.
- **Инкрементальность**: коммит на своей ветке после каждого законченного шага; после каждого шага дописать строку `Ход: <дата> <что сделано> <что дальше>` в секцию своей задачи в файле плана.
- **Советник**: вопросы пачкой, один dispatch с `wait_seconds`, а не по одному.
- **Формат результата**: первая строка `Статус: готово` или `Статус: не готово`; таблица файлов (путь, что изменено); прогнанные тесты и их выход; отклонения от плана с ответом советника; открытые вопросы. Без кода и диффов в ответе.

## 9. Скорость и параллелизм

- Потолки: 3 Claude, 3 Codex, 5 GLM одновременно, итого до 11 исполнителей; лимит `delegation.max_children` (здесь 16) выше, запас на советника и гейты.
- Вопросы советнику пачкой; командир не рассылает статусы, только точки решения v2 §10.
- Мелочь не ждёт полос: одна сессия от брифа до пре-гейта.

## 10. Первый прогон = замер

Не замерены: Sol на `high`, Terra с подтверждениями, лимит Codex при трёх Luna параллельно. Первый прогон по схеме считается замером. В итоге командир добавляет таблицу: доля токенов по вендору, effort по каждой задаче, сработавшие триггеры фолбека, число кругов гейта. По ней owner решает, куда сдвинуть доли; после этого схема въезжает в шаблон (раздел 12).

## 11. Честные границы

Как в v2 §12: всё prompt-soft. Классификацию размера, выбор effort, балансировку и триггеры движок не проверяет; нарушение = деградация оркестрации, не ошибка движка. Исполнение в gateway не добавлять.

## 12. Где живёт и порядок внедрения

Всё в одной ветке dev и одном PR (решение owner: сразу в бинарь):

- **Движок**: раздел 5.1 (три правки, тесты).
- **Шаблон**: `crates/ccteam-core/src/config.rs` `commander_quick_template()` + литеральные тесты; `crates/ccteam-web/web/src/lib/i18n.ts` `tplCommanderD`/`tplCommanderP` zh/ru/en + vitest (`i18n.test.ts`, `playbooks.test.ts`); `playbooks.ts` `vendors` карточки Commander остаётся `["claude", "codex", "opencode"]`.
